## 数据抓取与清洗

### 概述

数据抓取和清洗是数据处理的第一步，确保原始数据被正确清理和标准化。

### 主要步骤

#### Step 3.1: 数据清理

**脚本位置**: `Human-SIG/src/processing/clean_raw_data.py`

**功能**:
- 移除公司名称前缀和后缀（如 "OpenAI", "Mistral AI", "IBM" 等）
- 标准化模型名称格式
- 处理特殊字符和格式问题

**处理内容**:
1. **公司名称清理**:
   - 使用 `KNOWN_ORGS` 列表移除已知的组织名称
   - 迭代检查并移除前缀和后缀
   - 处理格式如：`Large 2Mistral AI` → `Large 2`

2. **格式标准化**:
   - 统一空格、连字符、下划线等分隔符
   - 处理特殊字符

**输出位置**: `Human-SIG/data/cleaned/`

**注意事项**:
- 如果发现新的公司名称未被清理，需要在 `clean_raw_data.py` 的 `KNOWN_ORGS` 列表中添加
- 建议在运行实体解析之前检查 `data/cleaned/` 中的数据是否还有公司名称残留

## 模型信息提取

### 概述

从清理后的数据中提取模型的结构化信息，包括家族、子家族、版本号、日期、参数量等。

### 脚本位置

**主脚本**: `Human-SIG/src/processing/extract_model_info.py`

### 提取的字段

每个模型名称会被解析为以下结构化信息：

| 字段 | 说明 | 示例 |
|------|------|------|
| `family` | 模型家族 | `gpt`, `gemini`, `claude` |
| `subfamily` | 子家族 | `gpt-5`, `gemini-pro`, `claude-opus` |
| `version` | 版本号 | `5`, `3.5`, `2.1`（已标准化：3=3.0） |
| `date` | 日期 | `2025-01-01` |
| `parameters` | 参数量 | `32B`, `1.5B`, `72B` |
| `other_info` | 其他信息 | 括号内容、变体标记等 |

### 提取逻辑

#### 1. 家族提取

- 使用已知家族列表（`FAMILIES`）进行匹配
- 支持特殊模型系列（`SPECIAL_MODEL_SERIES`），如 `o1`, `o3`, `o4`, `o5`
- 使用单词边界匹配，避免误匹配（如 "gemini" 不会提取 "mini"）

#### 2. 子家族提取

- 家族特定规则（如 GPT、Gemini、Claude 等）
- 通用变体关键词（`nano`, `pro`, `preview`, `mini`, `flash`, `ultra`, `turbo` 等）
- 按原始模型名称中的顺序组合

#### 3. 版本号提取

- 支持多种格式：`v3.5`, `3.5`, `3`
- 版本号标准化：`3.0` 和 `3` 视为相同

#### 4. 日期提取

- 支持多种格式：`YYYY-MM-DD`, `YYYYMMDD`, `MM-DD`
- 不参与匹配判断（已删除日期筛选）

#### 5. 参数量提取

- 格式：`32B`, `1.5B`, `72B`, `1T`
- 排除上下文大小（如 `32k`）

#### 6. 其他信息提取

**重要修复**: `other_info` 采用"剩余信息"策略：
- 从原始模型名称中移除已提取的信息（家族、子家族、版本、日期、参数量）
- 剩余部分即为 `other_info`
- 确保所有信息都被正确分类，不会重复提取

**示例**:
- `"Gemini 3 Pro"` → `other_info: null`（"Pro"已在subfamily中）
- `"GPT-5.1 (high)"` → `other_info: ["high"]`（括号内容）
- `"Qwen2.5 32B Instruct"` → `other_info: ["Instruct"]`

### 输出文件

#### 1. 各benchmark的模型信息

位置: `Human-SIG/data/processed/model_extraction/{benchmark}_models.json`

- 每个benchmark一个文件
- `artificial_analysis` 只生成一个文件（应用到所有10个benchmark）

#### 2. 所有模型的汇总信息

位置: `Human-SIG/data/processed/model_extraction/all_models_info.json`

- 包含所有benchmark中出现的所有唯一模型
- 去重存储（同一个模型名称只存储一份信息）
- 用于参考查询和调试验证

### 特殊处理

#### artificial_analysis

- 所有 `artificial_analysis` 子benchmark的模型名称相同
- 只提取一次，生成一个模型信息文件
- 该文件会应用到所有10个benchmark

#### LMArena

- 只处理 `lmarena/overall/data.csv`
- 自动过滤：只保留 `Score >= 1330` 的模型
- Score处理：支持 "1443Preliminary" 格式（移除"Preliminary"后缀）

## 实体解析算法

### 概述

实体解析是将benchmark中的模型名称映射到LMArena标准化的模型ID的过程。采用**结构化解析 + 分层过滤**的策略，大幅减少候选数量。

### 核心问题

传统模糊匹配方法存在的问题：
1. **跨家族误匹配**：`gpt-4` 和 `glm-4` 的字符串相似度很高，但它们是不同的模型
2. **格式差异无法识别**：`GPT-5.1 (high)` 和 `gpt-5.1-high` 应该匹配
3. **候选数量过多**：会产生数万个候选，无法人工审核

### 解决方案

#### 1. 结构化解析

将模型名称分解为语义组件：
- **家族名（family）**：如 `gpt`, `claude`, `gemini`
- **版本号（version）**：如 `5.1`, `4.5`, `3.2`
- **变体标记（variant）**：如 `high`, `medium`, `thinking`
- **日期（date）**：如 `20251101`

**示例**:
```
输入: "GPT-5.1 (high)"
解析结果:
  - family: "gpt"
  - version: "5.1"
  - variant: {"high"}
  - normalized: "gpt-5.1-high"
```

#### 2. 分层匹配策略

```
Level 0: 全局精确匹配（低ELO过滤）
  ↓ 未匹配
Level 1: 研究宇宙精确匹配（ELO >= 1330）
  ↓ 未匹配
Level 2: 映射表查找（mapping.json）
  ↓ 未匹配
Level 3: 结构化匹配
  ├─ 解析benchmark模型名称
  ├─ 基于家族过滤LMArena候选
  ├─ 计算结构化相似度
  ├─ 阈值过滤（相似度 > 0.3）
  └─ Top-K选择（最多3个候选）
```

#### 3. 结构化相似度计算

加权平均：
- **家族匹配**：40% 权重（必须满足）
- **版本相似度**：30% 权重
- **变体重叠度**：20% 权重
- **字符串相似度**：10% 权重（辅助指标）

**家族匹配规则**:
- 完全相同 → 1.0
- 包含关系（如 `gpt` 包含在 `gpt-5` 中）→ 0.9
- 字符串相似度 > 0.7 → 部分匹配
- **否则 → 0.0（直接淘汰，防止跨家族误匹配）**

**版本相似度**:
- 版本号完全相同 → 1.0
- 数值接近度：`1 / (1 + |v1 - v2|)`
  - 例如：5.1 和 5.2 → 0.5
  - 例如：5.1 和 5.0 → 0.91

**变体重叠度**:
- Jaccard相似度：`交集大小 / 并集大小`
- 例如：`{high, thinking}` 和 `{high}` → 0.5

### 优化效果

| 方法 | 候选数量 | 可审核性 |
|------|---------|---------|
| 传统方法 | 50,000+ | 不可管理 |
| 新方法 | 500-2,000 | 可管理 |
| **减少比例** | **94%** | - |

### 匹配规则

#### 必须一致的信息

1. **家族（family）**：必须完全一致
2. **子家族（subfamily）**：必须完全一致（如果都有）
3. **版本号（version）**：必须一致（标准化后：3=3.0）

#### 如果都有且不一致则排除

- **参数量（parameters）**：如果两个都有且不一致，不匹配

#### 不影响匹配

- **日期（date）**：不参与匹配判断
- **other_info**：不影响匹配

### 特殊处理

#### 1. 特殊模型系列（o1, o3, o4, o5）

- `o1` 和 `o3` 被视为不同的模型系列
- 必须精确匹配：`o1` 不会匹配 `o3-xxx`
- 即使都是 OpenAI 的模型，也不互相匹配

#### 2. 格式多样性

- **点号处理**：`GPT-4.5` → `gpt-4-5`
- **空格/下划线处理**：`GPT 4.5` → `gpt-4-5`
- **括号处理**：`GPT-5.1 (high)` → 变体: `{high}`

#### 3. 公司名称后缀

- 主要依赖 Step 3.1 的数据清理阶段处理
- 实体解析阶段也能容错（只要家族名能正确提取）

### 输出文件

#### 审核文件（JSON格式）

位置: `Human-SIG/data/processed/entity_resolution/review_files_v2/`

格式:
```json
{
  "benchmark_model_name": {
    "benchmark_info": {
      "family": "gpt",
      "subfamily": "gpt-5",
      "version": "5",
      ...
    },
    "candidates": [
      {
        "lmarena_model": "gpt-5-high",
        "family": "gpt",
        "subfamily": "gpt-5",
        "version": "5",
        ...
      }
    ]
  }
}
```

**审核规则**:
- 每个模型只保留一个候选（删除其他不正确的候选）
- 如果未找到匹配，保留 `[{"lmarena_model": "NO_MATCH_FOUND"}]`

### 应用审核结果

**脚本**: `Human-SIG/src/processing/apply_review_results_v2.py`

**功能**:
- 读取JSON格式的审核文件
- 提取每个模型的最终映射（candidates数组中的第一个元素）
- 更新 `config/mapping.json`

## 常见问题解答

### Q1: o1 和 o3 会混淆吗？

**A**: ✅ **不会混淆**

- `o1` 和 `o3` 被视为不同的模型系列
- 必须精确匹配：`o1` 只会匹配 LMArena 中以 `o1` 开头的模型
- `o1` **不会**匹配 `o3-xxx`，即使它们都是 OpenAI 的模型

**解决方案**:
- 定义了 `SPECIAL_MODEL_SERIES = {'o1', 'o3', 'o4', 'o5'}`
- 特殊模型系列必须精确匹配

### Q2: 格式多样性（空格、连字符、点号、括号）能正确识别吗？

**A**: ✅ **都能正确识别**

**处理方式**:
1. **点号处理**：`GPT-4.5` → `gpt-4-5`
2. **空格/下划线处理**：`GPT 4.5` → `gpt-4-5`
3. **括号处理**：`GPT-5.1 (high)` → 变体: `{high}`

**示例**:
- `GPT-4.5`, `GPT 4.5`, `GPT_4.5`, `gpt-4-5` 都会被标准化为 `gpt-4-5`，可以互相匹配 ✅

### Q3: 公司名称后缀能正确识别吗？

**A**: ✅ **可以识别，但主要依赖数据清理阶段**

**解决方案**:
1. **Step 3.1 数据清理**：使用 `KNOWN_ORGS` 列表移除公司名称
2. **实体解析阶段容错**：即使公司名称没有被完全清理，只要家族名能正确提取，仍可匹配

**注意事项**:
- 如果发现新的公司名称未被清理，需要在 `clean_raw_data.py` 的 `KNOWN_ORGS` 列表中添加

### Q4: 能保证所有可能匹配都被包含吗？

**A**: ✅ **保证所有可能匹配都被包含**

**解决方案**:
采用**双重匹配策略**：
1. **结构化匹配**（主要策略）：基于家族、版本、变体，阈值 0.3
2. **字符串相似度补充**（备选策略）：当结构化匹配候选不足时，阈值 0.6
3. **Fallback**（最终保障）：当家族提取完全失败时，阈值 0.5

**保证机制**:
- ✅ Level 0-2：精确匹配和映射表（100%准确）
- ✅ Level 3a：结构化匹配（覆盖大部分情况）
- ✅ Level 3b：字符串相似度补充（覆盖边缘情况）
- ✅ Level 3c：Fallback（覆盖极端情况）

### Q5: 为什么 other_info 会从 "Gemini" 中提取 "mini"？

**A**: ✅ **已修复**

**修复方案**:
- 采用"剩余信息"策略：从原始模型名称中移除已提取的信息
- 使用单词边界匹配，避免误匹配
- 确保所有信息都被正确分类到相应字段

**修复后**:
- `"Gemini 3 Pro"` → `other_info: null`（"Pro"已在subfamily中）✅
- `"Gemini 3 Flash"` → `other_info: null`（"Flash"已在subfamily中）✅

### Q6: 版本号 3 和 3.0 会被视为相同吗？

**A**: ✅ **是的**

- 版本号已标准化：`3.0` 和 `3` 视为相同
- 在匹配判断中，标准化后的版本号会进行比较

### Q7: 日期会影响匹配吗？

**A**: ❌ **不影响**

- 日期筛选已删除
- 不同格式的日期（如 "dec" 和 "1201"）不会影响匹配判断

### Q8: artificial_analysis 的映射如何应用？

**A**: **只需审核一个文件**

- `artificial_analysis_review.json` 会应用到所有10个benchmark
- 审核完成后，运行 `apply_review_results_v2.py`，脚本会自动将映射应用到所有10个benchmark
